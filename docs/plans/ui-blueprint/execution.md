# Координация исполнения

Предложение к [PLAN.UIB@1](../ui-blueprint-development.md); активируется при его
одобрении и запуске. Сейчас не разрешает запуск задач. Единственное состояние
исполнения хранится в [реестре](task-registry.md), а не в памяти разных чатов.

## Чаты и роль этого чата

Использовать отдельные видимые чаты одного проекта для длительных направлений
Web, Native и Core; давать им по одному конечному пакету. Не создавать отдельные
проекты/репозитории на модуль. Новый чат получает [пакет](packets.md), не fork
полной истории оркестратора. Для независимого review всегда свежий контекст.
Короткие одноразовые исследования могут быть подагентами лишь в пределах
явного разрешения пользователя; нет необходимости смешивать оба механизма.

Root хранит цель, граф зависимостей, принятые решения, владельцев и приёмку.
По прямому пожеланию пользователя «ты тоже писал код» от 2026-10-06 предлагается
локальное исключение из coordinator-only роли глобального root-orchestration:
root может брать один bounded пакет кода/интеграции или маршрутизации контрактов
C00 с теми же scope/checks и без самостоятельного расширения продуктового смысла.
Глобальные файлы не меняются; исключение не даёт права на broad refactor,
самостоятельную независимую приёмку своего кода или нарушение ресурсных границ.
Оно действует только внутри запущенного согласованного плана этого проекта.

Подходящие собственные задачи root: узкая schema/API интеграция, Cargo wiring,
CLI composition, конкретный детерминированный helper. Большие реализации,
upstream-обзоры, runtime QA и сырые логи остаются в конечных рабочих пакетах.
Если собственная задача мешает отвечать рабочим чатам, root возвращает её в очередь.

## Один checkout: владение и Git

- Все работают в текущей `master`. Другие ветки/worktrees требуют отдельного запроса.
- Один писатель на файл; отдельные модули одного crate допустимы при disjoint files.
- Root владеет root Cargo.toml/lockfile, schema/plugin API, CLI wiring, реестром
  и общей документацией. Перед передачей такого файла аренда меняется явно.
- Web/Native/Core/Export получают только нужные paths и symbols. `lib.rs`, общий
  manifest и shared fixtures не редактируются двумя владельцами одновременно.
- Workspace mutation и lockfile updates сериализуются. Cargo используют --locked;
  пересборки и workspace fmt не должны изменять чужой незавершённый код.
- Git index общий: stage/commit получает одного владельца. Перед grant сверяются
  paths и пустота index; чужой staged diff не трогают и не включают в коммит.
- Каждый изменяющий файлы пакет заканчивается своим path-limited checkpoint
  в текущей ветке; root выдаёт Git-аренду исполнителю и принимает его receipt.
  Commit сохраняет кандидата, но не означает product acceptance.
- Перед checkpoint build/review вводится короткий write barrier для затронутого
  набора; проверяется неизменность diff и фиксируется точный commit/build identity.
- Проверки, потребляющие shared owners, проходят на согласованном интегрированном
  состоянии. «Компилируется с незакоммиченным кодом соседа» не считается приёмкой.
- Никаких reset/clean/stash/revert чужих изменений. Конфликт scope возвращается root.

## Ресурсы и управление

Физический ввод/фокус имеют одного владельца; native и browser QA, если они
используют общий desktop, выполняются по очереди. Раздельно адресуемые ресурсы
параллельны только при доказанной изоляции. Не брать чужой процесс/сессию.
Root получает результат через ожидание статуса и финальный receipt чата; worker
не обязан сам писать другому чату. Follow-up идёт в исходный чат-владелец,
не запускает конкурирующую замену. Nested delegation по умолчанию запрещена.

Нужный shared API change: запрос с consumer/expected contract → согласование
ревизии → одна интеграция → перепроверка только affected consumers. При смене
контракта открытые зависимые пакеты перевалидируются; unaffected продолжаются.
Ждать только после отправки всех готовых безопасных задач. При waiting_resource
освободить слот/ресурс, сохранить owner/причину и recheck через три минуты.
Missing proof остаётся waiting_evidence; missing authority — awaiting_authority.
Платформенные пределы goal tools имеют приоритет над локальными правилами.

## Контекст, отчёты и восстановление

Root читает компактный receipt: результат, revision, changed paths, проверки,
расхождение, residual и следующая зависимость. Исходный лог запрашивается только
для конкретной ошибки. Worker завершает пакет и ждёт; бесконечных своих целей нет.
В checkpoint хранить намерение/решения/код/синтетические fixtures и короткий
acceptance summary. Сырые captures/логи не коммитить: task-temp для одноразового
запуска; нужные P7 evidence — отдельный application-state каталог с owner и
retention до принятия milestone/решения пользователя. Точное место фиксирует C01.
Registry ссылается на evidence; отсутствие или устаревание ссылки не скрывается.
После compaction: цель → фактическое разрешение → approved plan revision →
реестр → текущие аренды/receipt → актуальный route следующего пакета. Не перечитывать
весь upstream и не создавать заново завершённые задачи. Пауза — только по пользователю.

> по execution.md. Сначала C00, затем готовые задачи реестра. Соблюдай приёмку
> обеих платформ и продолжай без повторных подтверждений внутри этого объёма.

Перед create_thread выбрать этот проект из list_projects; никаких worktree
или смены модели по умолчанию. Сохранить возвращённые chat IDs в реестре.
Использовать create_goal только после явного запуска; численный бюджет не выдумывать.
Goal содержит результат P0–P7, критерии [приёмки](acceptance.md), границы и путь
к одобренному плану. Goal не планировщик отдельных чатов и не заменяет реестр.
Это соответствует [официальному описанию Goals](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex): цель привязана к чату и проверяемому исходу.
