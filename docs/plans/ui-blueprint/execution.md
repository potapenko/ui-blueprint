# Ранбук координации UI Blueprint

Исполнение [PLAN.UIB@1](../ui-blueprint-development.md) одобрено 2026-10-06 с
поправкой coordination-only для root. Единственное состояние
исполнения хранится в [реестре](task-registry.md), а не в памяти разных чатов.
Это каноническое место правил исполнения; новые прямые уточнения пользователя
вносятся сюда, а изменяемые статусы/аренды/следующие действия — в реестр.
Основание — запуск цели и последующие прямые требования пользователя: несколько
параллельных чатов, консультации с авторами Mac/Web ТЗ, commit+push каждого
checkpoint, контроль завершения и архивирование ненужных чатов.
Ранбук действует только внутри этого разрешённого объёма, не выдаёт новых прав
на другие проекты и не заменяет глобальные инструкции или продуктовые контракты.

## Короткий цикл координатора

Уточнение пользователя 2026-10-06: «Какой ответ от меня нужен? Уже всё же
обсудили уже.» Root ошибочно распространил запрет на изменения в read-only review
на последующую реализацию уже одобренной цели. Исправления дефектов внутри
PLAN.UIB@1 выполняют владельцы по конечным repair-пакетам с повторной проверкой,
commit и push, без повторного разрешения на тот же объём. Сам reviewer остаётся
read-only. Это не разрешает новые функции, изменение требований или действия вне
согласованных границ. Прежние awaiting_authority по семи findings сняты; история
ревью сохраняется, текущее назначение фиксирует реестр.

Это порядок применения записанных ниже требований пользователя, а не новый
объём разработки. Владелец ранбука и реестра — root.

1. Восстановить разрешение и состояние из реестра; проверить фактические статусы
   уже запущенных чатов и их последние receipts.
2. Выдать все независимые готовые пакеты существующим или новым рабочим чатам
   этого проекта; закрепить пути, зависимости и общий ресурс за одним владельцем.
3. Продуктовые вопросы и запросы сложных тестовых примеров направить указанному
   ниже Mac- или Web-консультанту; сохранить ответ и его ограничения в файле.
4. На завершённом связном шаге получить scoped commit **и успешный push**:
   SHA, ветку, результат проверок и незакрытые условия записать в receipt/реестр.
   Если чат остановился раньше результата, продолжить его конечное задание.
5. Освободить аренды, записать следующий шаг. Завершённый ненужный чат
   архивировать после передачи результата; нужный следующему пакету — сохранить.
6. При новом пользовательском правиле обновить этот ранбук, при смене состояния —
   реестр. Координационные изменения также закончить commit и push.

Рабочие чаты получают ссылку на этот ранбук в пакете. Для возвращения к работе
достаточно начать с него и реестра; пересказывать всю историю чата не требуется.

## Параллельные рабочие чаты

Уточнение пользователя после первого W01 live failure: работа шла слишком
медленно, фактически оставался один активный чат, а число ревью не объясняло
продуктовый прогресс. Root признал задержку выдачи следующих заданий.
Ближайший приоритет — реальные UI-данные через рабочий observe. Независимые
готовые участки сразу продолжают существующие Web/Core/Native владельцы.
Завершённые review-сессии не считаются активными исполнителями. Не запускать
новые общие аудиты или повторять принятые проверки ради отчётности; обязательное
ревью группировать вокруг конкретного готового изменения и реального риска.
Фактический сбой вести к точному коду причины и исправлению владельцем, без
цепочки лишних согласований внутри уже одобренного объёма. Это не отменяет
privacy/ownership/cleanup требования и не разрешает менять limits ради pass.

Использовать отдельные видимые чаты одного проекта для длительных направлений
Web, Native и Core; давать им по одному конечному пакету. Не создавать отдельные
проекты/репозитории на модуль. Новый чат получает [пакет](packets.md), не fork
полной истории оркестратора. Для независимого review всегда свежий контекст.
Короткие одноразовые исследования могут быть подагентами лишь в пределах
явного разрешения пользователя; нет необходимости смешивать оба механизма.

Не удерживать всё исполнение в одном чате, если есть независимые готовые части.
Запускать их параллельно, с разными write sets и конечными результатами. Если
общий контракт ещё меняется, отделять доступную fixture/build подготовку от
зависящей от него привязки; общий proof — только на точном committed baseline.
Не создавать лишние задания ради числа активных чатов. Сериализовать фактический
общий ресурс, а не всё направление. После checkpoint проверять готовность новой
параллельной работы, не ждать формального окончания соседних строк плана.

## Роль координатора

Root хранит цель, граф зависимостей, принятые решения, владельцев и приёмку.
Последнее прямое решение пользователя: «лучше, наверное, не писать код, только
координация». Оно отменяет предлагавшееся исключение для root. Применяется
глобальный root-orchestration: root не пишет продуктовый код/документацию,
не исследует продуктовые исходники и не выполняет build/test/runtime/visual QA.
Root поддерживает координационные документы, выдаёт задания, принимает scoped
receipts и сохраняет координационные checkpoint. C00 выполняет spec worker;
Cargo/schema/CLI/integration — отдельный Integration worker. Глобальные файлы
не меняются. Самопроверка исполнителя не называется независимой приёмкой.

## Один checkout: владение и Git

- Все работают в текущей `master`. Другие ветки/worktrees требуют отдельного запроса.
- Один писатель на файл; отдельные модули одного crate допустимы при disjoint files.
- Integration worker владеет root Cargo.toml/lockfile и schema/plugin API;
  CLI получает отдельного назначенного L01 владельца, engine — Core. Root владеет
  реестром/пакетами. Продуктовую документацию пишет назначенный worker.
- Web/Native/Core/Export получают только нужные paths и symbols. `lib.rs`, общий
  manifest и shared fixtures не редактируются двумя владельцами одновременно.
- Workspace mutation и lockfile updates сериализуются. Cargo используют --locked;
  пересборки и workspace fmt не должны изменять чужой незавершённый код.
- Git index общий: stage/commit получает одного владельца. Перед grant сверяются
  paths и пустота index; чужой staged diff не трогают и не включают в коммит.
- Каждый изменяющий файлы пакет заканчивается своим path-limited checkpoint
  и push в текущей ветке; root выдаёт Git-аренду исполнителю и принимает его receipt.
  Прямое уточнение пользователя 2026-10-06 требует commit **и push** после каждого
  checkpoint, в том числе от исполнителей; старые no-push указания пакетов отменены.
  В receipt обязательны SHA и результат push; при ошибке push работа не закрывается.
  Commit сохраняет кандидата, но не означает product acceptance.
- Не копить длинную работу до финального коммита: каждый завершённый связный шаг
  сохранять checkpoint+push. При срочном сохранении допустим честно отмеченный WIP.
  Это обязанность и root, и каждого исполнителя, а не только финального интегратора.
- Git-аренда короткая: checkpoint-ready → grant → проверить текущую ветку/index →
  stage только собственные согласованные paths → commit → push origin master →
  вернуть SHA/push/checks/residual → освободить аренду. Не занимать index на всё
  время написания кода. После успешного push проверить сохранённый SHA и статус
  своих paths. Не делать force-push или автоматически переписывать историю.
- Перед checkpoint build/review вводится короткий write barrier для затронутого
  набора; проверяется неизменность diff и фиксируется точный commit/build identity.
- Проверки, потребляющие shared owners, проходят на согласованном интегрированном
  состоянии. «Компилируется с незакоммиченным кодом соседа» не считается приёмкой.
- Никаких reset/clean/stash/revert чужих изменений. Конфликт scope возвращается root.

## Ресурсы и управление

Физический ввод/фокус имеют одного владельца; native и browser QA, если они
используют общий desktop, выполняются по очереди. Раздельно адресуемые ресурсы
параллельны только при доказанной изоляции. Не брать чужой процесс/сессию.
Root получает результат через ожидание статуса и финальный receipt чата; worker
не обязан сам писать другому чату. Follow-up идёт в исходный чат-владелец,
не запускает конкурирующую замену. Nested delegation по умолчанию запрещена.

Нужный shared API change: запрос с consumer/expected contract → согласование
ревизии → одна интеграция → перепроверка только affected consumers. При смене
контракта открытые зависимые пакеты перевалидируются; unaffected продолжаются.
Ждать только после отправки всех готовых безопасных задач. При waiting_resource
освободить слот/ресурс, сохранить owner/причину и recheck через три минуты.
Missing proof остаётся waiting_evidence; missing authority — awaiting_authority.
Платформенные пределы goal tools имеют приоритет над локальными правилами.

## Контроль чатов и архивирование

Root проверяет фактический status/turn через wait_threads, сохраняя отдельный
cursor каждого чата; таймаут ожидания не означает завершение или провал.
Для работающих задач — bounded ожидания, для задержки ресурса — recheck не позже
трёх минут. Не создавать дубликат исполнителя из-за долгого ответа.
Если чат стал idle/completed, прочитать финальный результат и сверить с packet:
остался разрешённый dependency-ready объём — явно отправить продолжение в этот
же чат; есть blocker — записать точную зависимость; всё готово — принять receipt.
Фраза исполнителя «продолжаю» не доказывает, что его следующий turn запущен.

После сохранения результата проверить, нужен ли контекст чата следующей задаче.
Ненужный завершённый чат архивировать через set_thread_archived; пользователь это
прямо поручил. Перед архивированием подтвердить terminal status, checkpoint/push
при изменениях файлов, receipt, передачу ресурсов и незавершённых зависимостей.
Не архивировать работающего владельца или единственного носителя непереданного
результата. Сохранить ID и причину в реестре; архивирование не удаляет историю,
артефакты или требуемые evidence и не меняет состояние Git.
Профильные консультанты и владельцы ближайших пакетов остаются, пока нужны.

## Контекст, отчёты и восстановление

Root читает компактный receipt: результат, revision, changed paths, проверки,
расхождение, residual и следующая зависимость. Исходный лог запрашивается только
для конкретной ошибки. Worker завершает пакет и ждёт; бесконечных своих целей нет.
В checkpoint хранить намерение/решения/код/синтетические fixtures и короткий
acceptance summary. Сырые captures/логи не коммитить.
Прямое уточнение пользователя 2026-10-07: результаты ImageGen сохраняются
по исходным путям инструмента, включая `$CODEX_HOME/generated_images/`.
Этот tool-managed каталог разрешён для таких deliverables. Не удалять,
перемещать, переименовывать или перезаписывать эти файлы и не включать их
в автоматическую/финальную очистку даже после inline показа. Общее поручение
очистить временные файлы не разрешает удаление ImageGen; нужен отдельный позднейший
прямой запрос пользователя, называющий удаляемые результаты. Это исключение
имеет приоритет над остальными правилами очистки ниже.
Позднейшее прямое правило
пользователя запрещает новые постоянные каталоги без его явного разрешения на
место и назначение; запись в плане/пакете сама такого разрешения не создаёт.
Для текущей операции использовать system-temp, после использования удалить только
свои файлы/пустые директории и подтвердить удаление. Не превращать их в архив P7.
Будущие runtime-пакеты наследуют это правило вместо прежней выдачи новых UUID
директорий в Application Support. Уже существующие evidence не удалять без
разрешения пользователя; ранее сохранённые записи остаются историческими.
Скриншоты показывать inline; временный путь/сообщение «сохранено» не заменяет
независимую передачу изображения. Сам показ не доказывает независимое сохранение:
если сообщение ссылается на локальный файл, не удалять его при очистке.
Не удалять файл, если это сломает уже выданное
изображение; при отсутствии независимой доставки назвать точное ограничение.
Registry ссылается на evidence; отсутствие или устаревание ссылки не скрывается.
После compaction: цель → фактическое разрешение → approved plan revision →
реестр → текущие аренды/receipt → актуальный route следующего пакета. Не перечитывать
весь upstream и не создавать заново завершённые задачи. Пауза — только по пользователю.

После применимых глобальных/repo instructions минимальный restart-набор:
этот ранбук → реестр → packet текущего владельца →
его последний receipt и точный commit/push → только применимый spec route.
В реестре сохранять owner chat/host, разрешение, write/Git/runtime leases, статус,
проверенный SHA, review/QA gaps, waiting reason и конкретный следующий шаг.
История чата помогает найти документы, но не служит единственным состоянием.
Нельзя восстанавливать полномочия из старой агентской сводки или молча отменять
прямое ограничение пользователя; отсутствующее разрешение остаётся awaiting_authority.

## Фактический запуск

Пользователь одобрил план и поручил начать цель; точная цитата в реестре.
Это разрешает предусмотренные планом рабочие чаты, конечные задания и follow-up.
Nested delegation не разрешена. Сохраняется исходная approved plan revision.

Перед create_thread выбрать этот проект из list_projects; никаких worktree
или смены модели по умолчанию. Сохранить возвращённые chat IDs в реестре.
Использовать create_goal только после явного запуска; численный бюджет не выдумывать.
Goal содержит результат P0–P7, критерии [приёмки](acceptance.md), границы и путь
к одобренному плану. Goal не планировщик отдельных чатов и не заменяет реестр.
Это соответствует [официальному описанию Goals](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex): цель привязана к чату и проверяемому исходу.
