# Ранбук координации UI Blueprint

Исполнение [PLAN.UIB@1](../ui-blueprint-development.md) одобрено 2026-10-06 с
поправкой coordination-only для root. Единственное состояние
исполнения хранится в [реестре](task-registry.md), а не в памяти разных чатов.
Это каноническое место правил исполнения; новые прямые уточнения пользователя
вносятся сюда, а изменяемые статусы/аренды/следующие действия — в реестр.
Основание — запуск цели и последующие прямые требования пользователя: несколько
параллельных чатов, консультации с авторами Mac/Web ТЗ, commit+push каждого
checkpoint, контроль завершения и архивирование ненужных чатов.
Ранбук действует только внутри этого разрешённого объёма, не выдаёт новых прав
на другие проекты и не заменяет глобальные инструкции или продуктовые контракты.

## Запрет управления Codex через Computer Use — 2026-10-10

Пользователь прямо отверг управление самим Codex через Computer Use. Root и
рабочие чаты не выполняют такое управление и не обходят запрет другим backend.
Координация использует штатные инструменты чатов. Историческое поручение Q02-R
остановить старый Q02 через UI отменено. Подтверждённый terminal status старого
исполнителя позволяет передать конечную задачу после проверки оставшихся ресурсов;
ручной Stop пользователя не требуется, если чат уже завершился.

Почему ты простоял столько времени? Почему вообще ты меня это спрашиваешь?

Для оставшихся Q02/Q03 разрешены необходимые запуски Mac/Web приложений,
обычный setup контрольных fixtures и ранее согласованных реальных примеров
PlayPhrase.me. Старые ограничения «только fixtures», «только уже запущенное» и
ожидания отдельного разрешения на запуск больше не действуют. Старый текст
host objective и исторических пакетов не отменяет это прямое указание.
Не спрашивать разрешение повторно. Чаты самостоятельно завершают свои задачи.
Это не разрешение менять данные/код чужих приложений, системные permissions,
проводить покупки или иные посторонние действия.

Q02 получает Native desktop и тихий CPU для конечных измерений; консультанты
готовят реальные случаи параллельно, а live-запуски/сбор делают после освобождения
измерительной полосы. Техническая сериализация общей среды не является новым
согласованием. Существующие source-project runtime reservations сохраняются.
Численные gates и quality требования неизменны; новый request-only workload
фиксируется с baseline до candidate timing, с явным отличием от старого input.

## Самостоятельные чаты-задачи — уточнение пользователя 2026-10-08

Основание: пользователь прямо потребовал «относительно небольшие, среднего
размера таски, как это в плане у нас написано» и полный цикл в каждом отдельном
чате: постановка, планирование, реализация, тестирование, готовый результат.
Это заменяет прежний порядок промежуточных поручений root. Предложение root
«Web целиком / Native целиком / Core целиком» отвергнуто и не применяется.

- Единица работы — одна самостоятельная задача среднего размера из плана с
  проверяемым пользовательским результатом. Ни целая платформа, ни отдельная
  правка, запуск теста, сохранение receipt или разрешение продолжить работу.
  Если строка плана слишком велика, разделять её по независимо принимаемым
  результатам; не дробить один результат на чаты «исследовать / написать /
  проверить / исправить». Число десять в примере пользователя не является квотой.
- Один видимый чат Codex — одна задача. Root передаёт результат, применимые
  требования, имеющиеся наработки, зависимости, защищённые границы и критерии
  готовности. Чат сам уточняет техническую постановку, записывает локальный план,
  читает нужный код, реализует, выбирает необходимые проверки, устраняет найденные
  ошибки, обновляет документацию, делает checkpoint commit и push. Выданная
  задача разрешает весь этот цикл; промежуточное одобрение root не требуется.
- Область владения задавать достаточно широкой для полного результата, включая
  непосредственно связанные тесты и документацию. Конкретные файлы внутри
  закреплённой области определяет исполнитель при планировании. Общие файлы
  имеют одного владельца; изменение чужого owner возвращается как конкретная
  зависимость. Границы продукта и полномочий остаются обязательными.
- Готовые независимые задачи запускать в отдельных чатах параллельно. Зависимые
  задачи остаются в очереди до готовности входов. Не плодить подготовительные
  поручения лишь для заполнения слотов. Уже завершённые части не делать заново.
- Root не назначает внутренние шаги, команды, исправления компиляции и обычные
  тестовые итерации. Не отправляет follow-up после каждого промежуточного
  сообщения. Получает финальный результат или реальный блокер. Если чат
  завершил turn до выполнения задания без блокера, возвращает ему ту же задачу
  целиком, а не проектирует очередной микрошаг.
- Финальный ответ чата: что работает, какие проверки выполнены и с каким
  результатом, commit SHA и push, изменённые области, оставшиеся ограничения.
  Root сверяет это с исходными критериями. Обязательное независимое ревью
  сохраняется для предусмотренных контрактом рисков и итоговой приёмки;
  отдельные ревью/activation gates на каждый внутренний шаг не вводятся.
- Чаты-задачи создаются через create_thread. Внутренние подагенты не подменяют
  эти чаты; новые подагенты и вложенная делегация для обычной разработки по
  этому порядку не запускаются. Отдельный явный запрос пользователя на review
  subagent рассматривается в собственных границах.
- Завершённый чат архивировать после сохранения результата и передачи нужных
  зависимостей. Консультантов Mac/Web сохранять и спрашивать по продуктовым
  неоднозначностям и содержательным примерам, как указано ниже.

### Практическая граница вмешательства

Повторное прямое требование пользователя: отдельный чат — самостоятельный таск,
который заканчивает весь цикл и сообщает результат. Одной записи этого принципа
недостаточно: root применяет его к каждому следующему сообщению и назначению.

- Промежуточный commentary, запуск команды, локальный тест или checkpoint не
  требуют ответа root. Не читать ход рассуждений и инструменты работающего чата
  ради управления следующим шагом. Ожидать завершение через компактный статус.
- Повод для сообщения исполнителю: готовая необходимая зависимость, конкретный
  конфликт владения/полномочий, обнаруженный дефект результата или новое указание
  пользователя. Обычный ход реализации остаётся внутри чата.
- Перед новой задачей проверить: может ли исполнитель закончить заявленный
  результат без последовательности новых поручений root? Если нет, дополнить
  исходную постановку и область владения. Не выдавать цепочку микрозаданий.
- Итог принимать одним сопоставлением результата с исходными критериями;
  обязательную независимую проверку выполнять в предусмотренной области риска.
  Не добавлять согласование каждого внутреннего шага или новые критерии после
  завершения. Исправления внутри задачи и повтор нужных тестов выполняет её владелец.
- В текущем состоянии реестра держать только актуальные задачи, результат и точную
  зависимость. Старые группы явно обозначать историей. Пользователю сообщать,
  какая возможность готова и что осталось до поставки, а не перечислять операции.

Root остаётся координатором задач и зависимостей. Его результат — выдача готовых
задач, приём завершённых результатов и итоговая поставка. Полный P0–P7, spec-first,
обязательные доказательства, текущая ветка и защита чужих изменений сохранены.
Этот раздел имеет приоритет над старой детализацией поручений в данном ранбуке
и исторических пакетах; старые запреты вне выданного outcome остаются в силе.

checkpoint и переводит цель в `paused`. Никакого автоматического возобновления;

## Главный продуктовый приоритет — 2026-10-08

Пользователь прямо напомнил: UI Blueprint помогает ИИ быстро получить геометрию
реального интерфейса для его разработки, сначала Web и Mac. Root ошибочно сделал
главным направлением развитие исполнителя действий. Следующий результат — удобный
read-only путь: выбранный компонент → реальные bounds/структура → размеры,
расстояния/отношения → компактный ответ и понятный геометрический diff.

Основание сверено с оригинальным UIB.TZ@1.4, разделами «Назначение», «Геометрия»,
«Выбор области», «Геометрические правила», «Консольный интерфейс», и PLAN.UIB@1
вехами C/D. Действия присутствуют в ТЗ как второй сценарий; их scope не удаляется,
но они не должны задерживать основную геометрическую пользу. Новое развитие P5
останавливается на ближайшем сохранённом checkpoint без потери сделанного кода.
Объём P0–P7 сохранён; изменение приоритета само по себе не меняет статус цели.

Read-only geometry не требует mutation-ready refs, nonce или завершённого executor.
Использовать уже работающие collectors/engine/CLI/probe. Не изобретать второй graph,
новые frameworks или ещё одну диагностическую платформу. Простые fixtures остаются
локальными oracle; полезность проверять на содержательном компоненте с несколькими
частями и действующим геометрическим вопросом. Mac/Web advisors дают существующие
кейсы/источники; это не разрешает менять или запускать чужой проект автоматически.
Скорость/удобство измерять на фактическом запросе, не выводить из Rust/числа тестов.

## Уточнение темпа и ревью — 2026-10-08

Пользователь спросил, оправдывает ли ревью задержку разработки, затем уточнил:
«Я вопрос просто задал… если это полезное действие, ну оставь, конечно».
Это НЕ запрет всех ревью. Первое сообщение root об отмене reviewer rounds было
поспешным и отозвано; полезная независимая проверка реальных рисков сохраняется.

Основной цикл — реализация законченного сценария, необходимые обычные тесты,
целевой end-to-end результат и commit+push. Не делать отдельные задания/ревью/
activation gates на каждую механическую правку, подготовку или receipt. Исполнитель
сам исправляет compiler/test/harness ошибки и продолжает свой разрешённый outcome.
Риск ввода, прав, privacy и ownership проверяется одним сфокусированным ревью
связного изменения; не повторять уже принятую проверку без нового основания.
Обычные контролируемые тесты своего fixture не ждут отдельного review каждой детали;
обязательная итоговая приёмка и её доказательства не отменены. Не заменять tests
бумажной сверкой и не превращать отсутствие findings в доказательство runtime.

Задачи P5, как и остальных этапов, выдаются по самостоятельным результатам
плана согласно уточнению выше. Названия платформ обозначают области кода, а не
бессрочные задания одному чату. Общий интерфейс передаётся зависимым задачам
один раз; техническая сериализация Git и общего desktop не становится отдельным
согласованием каждого внутреннего шага разработки.

## Короткий цикл координатора

Уточнение пользователя 2026-10-06: «Какой ответ от меня нужен? Уже всё же
обсудили уже.» Root ошибочно распространил запрет на изменения в read-only review
на последующую реализацию уже одобренной цели. Исправления дефектов внутри
PLAN.UIB@1 выполняют владельцы по конечным repair-пакетам с повторной проверкой,
commit и push, без повторного разрешения на тот же объём. Сам reviewer остаётся
read-only. Это не разрешает новые функции, изменение требований или действия вне
согласованных границ. Прежние awaiting_authority по семи findings сняты; история
ревью сохраняется, текущее назначение фиксирует реестр.

Это порядок применения записанных ниже требований пользователя, а не новый
объём разработки. Владелец ранбука и реестра — root.

1. Восстановить разрешение и состояние из реестра; проверить фактические статусы
   уже запущенных чатов и их последние receipts.
2. Выдать все независимые готовые пакеты существующим или новым рабочим чатам
   этого проекта; закрепить пути, зависимости и общий ресурс за одним владельцем.
3. Продуктовые вопросы и запросы сложных тестовых примеров направить указанному
   ниже Mac- или Web-консультанту; сохранить ответ и его ограничения в файле.
4. На завершённом связном шаге получить scoped commit **и успешный push**:
   SHA, ветку, результат проверок и незакрытые условия записать в receipt/реестр.
   Если чат остановился раньше результата, продолжить его конечное задание.
5. Освободить аренды, записать следующий шаг. Завершённый ненужный чат
   архивировать после передачи результата; нужный следующему пакету — сохранить.
6. При новом пользовательском правиле обновить этот ранбук, при смене состояния —
   реестр. Координационные изменения также закончить commit и push.

Рабочие чаты получают ссылку на этот ранбук в пакете. Для возвращения к работе
достаточно начать с него и реестра; пересказывать всю историю чата не требуется.

## Параллельные рабочие чаты

Уточнение пользователя после первого W01 live failure: работа шла слишком
медленно, фактически оставался один активный чат, а число ревью не объясняло
продуктовый прогресс. Root признал задержку выдачи следующих заданий.
Ближайший приоритет — реальные UI-данные через рабочий observe. Независимые
готовые участки сразу продолжают существующие Web/Core/Native владельцы.
Завершённые review-сессии не считаются активными исполнителями. Не запускать
новые общие аудиты или повторять принятые проверки ради отчётности; обязательное
ревью группировать вокруг конкретного готового изменения и реального риска.
Фактический сбой вести к точному коду причины и исправлению владельцем, без
цепочки лишних согласований внутри уже одобренного объёма. Это не отменяет
privacy/ownership/cleanup требования и не разрешает менять limits ради pass.

Использовать отдельные видимые чаты одного проекта для самостоятельных задач
среднего размера из плана, а не постоянные чаты на всю платформу. Не создавать отдельные
проекты/репозитории на модуль. Новый чат получает [пакет](packets.md), не fork
полной истории оркестратора. Для независимого review всегда свежий контекст.
Обычное исследование входит в полный цикл чата-задачи; отдельный подагент
для него по умолчанию не создаётся.

Не удерживать всё исполнение в одном чате, если есть независимые готовые части.
Запускать их параллельно, с разными write sets и конечными результатами. Если
общий контракт ещё меняется, отделять доступную fixture/build подготовку от
зависящей от него привязки; общий proof — только на точном committed baseline.
Не создавать лишние задания ради числа активных чатов. Сериализовать фактический
общий ресурс, а не всё направление. После checkpoint проверять готовность новой
параллельной работы, не ждать формального окончания соседних строк плана.

## Роль координатора

Root хранит цель, граф зависимостей, принятые решения, владельцев и приёмку.
Последнее прямое решение пользователя: «лучше, наверное, не писать код, только
координация». Оно отменяет предлагавшееся исключение для root. Применяется
глобальный root-orchestration: root не пишет продуктовый код/документацию,
не исследует продуктовые исходники и не выполняет build/test/runtime/visual QA.
Root поддерживает координационные документы, выдаёт задания, принимает scoped
receipts и сохраняет координационные checkpoint. C00 выполняет spec worker;
Cargo/schema/CLI/integration — отдельный Integration worker. Глобальные файлы
не меняются. Самопроверка исполнителя не называется независимой приёмкой.

## Один checkout: владение и Git

- Все работают в текущей `master`. Другие ветки/worktrees требуют отдельного запроса.
- Один писатель на файл; отдельные модули одного crate допустимы при disjoint files.
- Integration worker владеет root Cargo.toml/lockfile и schema/plugin API;
  CLI получает отдельного назначенного L01 владельца, engine — Core. Root владеет
  реестром/пакетами. Продуктовую документацию пишет назначенный worker.
- Web/Native/Core/Export получают только нужные paths и symbols. `lib.rs`, общий
  manifest и shared fixtures не редактируются двумя владельцами одновременно.
- Workspace mutation и lockfile updates сериализуются. Cargo используют --locked;
  пересборки и workspace fmt не должны изменять чужой незавершённый код.
- Git index общий: stage/commit получает одного владельца. Перед сохранением проверяются
  владение lane, paths и пустота index; чужой staged diff не трогают и не включают в коммит.
- Каждый изменяющий файлы пакет заканчивается своим path-limited checkpoint
  и push в текущей ветке; исполнитель самостоятельно выполняет сохранение в технически свободном Git lane.
  Прямое уточнение пользователя 2026-10-06 требует commit **и push** после каждого
  checkpoint, в том числе от исполнителей; старые no-push указания пакетов отменены.
  В receipt обязательны SHA и результат push; при ошибке push работа не закрывается.
  Commit сохраняет кандидата, но не означает product acceptance.
- Не копить длинную работу до финального коммита: каждый завершённый связный шаг
  сохранять checkpoint+push. При срочном сохранении допустим честно отмеченный WIP.
  Это обязанность и root, и каждого исполнителя, а не только финального интегратора.
- Git-аренда короткая и техническая, без одобрения кода root: занять свободный
  lane согласованным при выдаче задачи способом → проверить текущую ветку/index →
  stage только собственные согласованные paths → commit → push origin master →
  вернуть SHA/push/checks/residual → освободить аренду. Не занимать index на всё
  время написания кода. Нельзя считать пустой index достаточным доказательством
  свободного lane: способ взаимного исключения должен быть задан до параллельной
  записи. Ожидание занятого lane не останавливает независимую работу задачи.
  После успешного push проверить сохранённый SHA и статус
  своих paths. Не делать force-push или автоматически переписывать историю.
- Перед checkpoint build/review вводится короткий write barrier для затронутого
  набора; проверяется неизменность diff и фиксируется точный commit/build identity.
- Проверки, потребляющие shared owners, проходят на согласованном интегрированном
  состоянии. «Компилируется с незакоммиченным кодом соседа» не считается приёмкой.
- Никаких reset/clean/stash/revert чужих изменений. Конфликт scope возвращается root.

## Ресурсы и управление

Физический ввод/фокус имеют одного владельца; native и browser QA, если они
используют общий desktop, выполняются по очереди. Раздельно адресуемые ресурсы
параллельны только при доказанной изоляции. Не брать чужой процесс/сессию.
Root получает результат через ожидание статуса и финальный receipt чата; worker
не обязан сам писать другому чату. Follow-up идёт в исходный чат-владелец,
не запускает конкурирующую замену. Nested delegation по умолчанию запрещена.

Shared API, уже входящий в задачу его владельца, реализуется им без отдельного
поручения root; зависимым чатам передаётся готовый контракт. Новый конфликт
владения или выход за согласованный scope возвращается как конкретный блокер. При смене
контракта открытые зависимые пакеты перевалидируются; unaffected продолжаются.
Ждать только после отправки всех готовых безопасных задач. При waiting_resource
освободить слот/ресурс, сохранить owner/причину и recheck через три минуты.
Missing proof остаётся waiting_evidence; missing authority — awaiting_authority.
Платформенные пределы goal tools имеют приоритет над локальными правилами.

## Контроль чатов и архивирование

Root проверяет фактический status/turn через wait_threads, сохраняя отдельный
cursor каждого чата; таймаут ожидания не означает завершение или провал.
Для работающих задач — bounded ожидания, для задержки ресурса — recheck не позже
трёх минут. Не создавать дубликат исполнителя из-за долгого ответа.
Если чат стал idle/completed, прочитать финальный результат и сверить с packet:
остался разрешённый dependency-ready объём — явно отправить продолжение в этот
же чат; есть blocker — записать точную зависимость; всё готово — принять receipt.
Фраза исполнителя «продолжаю» не доказывает, что его следующий turn запущен.

После сохранения результата проверить, нужен ли контекст чата следующей задаче.
Ненужный завершённый чат архивировать через set_thread_archived; пользователь это
прямо поручил. Перед архивированием подтвердить terminal status, checkpoint/push
при изменениях файлов, receipt, передачу ресурсов и незавершённых зависимостей.
Не архивировать работающего владельца или единственного носителя непереданного
результата. Сохранить ID и причину в реестре; архивирование не удаляет историю,
артефакты или требуемые evidence и не меняет состояние Git.
Профильные консультанты и владельцы ближайших пакетов остаются, пока нужны.

## Контекст, отчёты и восстановление

Root читает компактный receipt: результат, revision, changed paths, проверки,
расхождение, residual и следующая зависимость. Исходный лог запрашивается только
для конкретной ошибки. Worker завершает пакет и ждёт; бесконечных своих целей нет.
В checkpoint хранить намерение/решения/код/синтетические fixtures и короткий
acceptance summary. Сырые captures/логи не коммитить.
Последнее прямое уточнение пользователя 2026-10-07 заменяет прежнее исключение
только для ImageGen: ВСЕ создаваемые изображения (ImageGen, screenshots, crops,
mockups и промежуточные варианты) сохраняются в системном temp (`$TMPDIR`/system
API), никогда в repository-local tmp. Уникальные task-каталоги там разрешены.
Не удалять изображения или содержащие их каталоги ни во время работы, ни в конце,
даже после inline показа. Исключить их из любой очистки; lifecycle оставлен ОС или
пользователю, без обещания срока или удаления при каждой перезагрузке.
Если инструмент не позволяет выбрать destination, скопировать результат в system
temp, сохранив original без удаления/перемещения/переименования/перезаписи; для
новых embeds использовать temp-копию и сообщить, что tool-managed original остаётся.
Старые изображения/assets не переносить задним числом и не ломать ссылки. Другая
папка или удаление требуют позднейшего явного запроса о конкретных файлах.
Показывать изображения inline; ссылка/сообщение «сохранено» не заменяет показ.
Ни проверка chat retention, ни cleanup receipt для изображений не требуются.
Это правило имеет приоритет над screenshot/evidence/skill/project cleanup.
Новые постоянные каталоги иначе не разрешены без прямого указания места и цели.
Обычные не-image output/build/cache файлы текущей операции хранить в system temp,
удалять только свои после использования и проверять удаление. Никогда не выполнять
recursive removal каталога с сохраняемыми изображениями. Уже существующие evidence
не удалять без разрешения; исторические записи сохраняют исходный статус.
Registry ссылается на evidence; отсутствие или устаревание ссылки не скрывается.
После compaction: цель → фактическое разрешение → approved plan revision →
реестр → текущие аренды/receipt → актуальный route следующего пакета. Не перечитывать
весь upstream и не создавать заново завершённые задачи. Пауза — только по пользователю.

После применимых глобальных/repo instructions минимальный restart-набор:
этот ранбук → реестр → packet текущего владельца →
его последний receipt и точный commit/push → только применимый spec route.
В реестре сохранять owner chat/host, разрешение, write/Git/runtime leases, статус,
проверенный SHA, review/QA gaps, waiting reason и конкретный следующий шаг.
История чата помогает найти документы, но не служит единственным состоянием.
Нельзя восстанавливать полномочия из старой агентской сводки или молча отменять
прямое ограничение пользователя; отсутствующее разрешение остаётся awaiting_authority.

## Фактический запуск

Пользователь одобрил план и поручил начать цель; точная цитата в реестре.
Это разрешает предусмотренные планом рабочие чаты, конечные задания и follow-up.
Nested delegation не разрешена. Сохраняется исходная approved plan revision.

Перед create_thread выбрать этот проект из list_projects; никаких worktree
или смены модели по умолчанию. Сохранить возвращённые chat IDs в реестре.
Использовать create_goal только после явного запуска; численный бюджет не выдумывать.
Goal содержит результат P0–P7, критерии [приёмки](acceptance.md), границы и путь
к одобренному плану. Goal не планировщик отдельных чатов и не заменяет реестр.
Это соответствует [официальному описанию Goals](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex): цель привязана к чату и проверяемому исходу.
