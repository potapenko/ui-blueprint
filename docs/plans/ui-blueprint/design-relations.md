# Понятная математика интерфейса

Дата: 2026-10-11. Статус: реализация выполнена; ниже сохранены исходный план и история согласования.
Основание: пользователь попросил исследовать математические связи размеров, шкалы и понятное объяснение решений, поискать научные/дизайн-источники и создать цель. Это новая single-agent исследовательская цель; прежние принятые цели не переоткрываются. Документ — предложение, не Active product contract.
Потребитель: решение о добавлении объяснимых отношений в измерения и автоматически создаваемый ImageGen prompt. Task-owned write set: этот файл и запись в [реестре задач](task-registry.md); код, спецификации и изображения не меняются.

## Вывод

Предлагаю описывать интерфейс через короткие проверяемые отношения: равные колонки, общий край, повторяющийся размер, шаг рядов, отношение отступов. Человек получает объяснение рядом с формулой; AI — точные операнды и происхождение. Главная польза: можно понять и воспроизвести структуру без перечитывания десятков несвязанных чисел.
Отдельно отвечаем на три вопроса: **что измерено**, **как размеры связаны**, **почему принято решение**. Первые два часто доступны из геометрии. Третий требует декларации, спецификации или зафиксированного решения автора. Убедительная математическая связь сама по себе не раскрывает намерение дизайнера.

## Предлагаемая модель доказательств

| Вид утверждения | Пример | Необходимое основание |
| --- | --- | --- |
| Измерение | «Зазор между полями — 8 CSS px». | Узлы/края, bounds kind, Observation, пространство/единицы и coverage. |
| Вычисленная связь | «Два равных поля заполняют строку: 2 × 179 + 8 = 366». | Проверенные движком операнды, выражение, результат и отклонение. Это связь в данном наблюдении. |
| Гипотеза о системе | «Отступы этого семейства совместимы с шагом 4». | Названное семейство, набор измерений, исключения и альтернативы. Не доказательство design token. |
| Подтверждённое основание | «Компонент использует spacing.control; он ссылается на space.2». | Действительная привязка декларации/токена к компоненту и версии. Объяснение мотива выбора — только если оно есть в авторском решении. |
| Предложение изменения | «Предлагаем унифицировать эти два зазора». | Отдельный proposed результат, без подмены наблюдаемой геометрии. Не входит в первый этап. |

Математический словарь: равенство размеров `w₁=w₂`; пропорция `a=k×b`; распределение `n×w+(n−1)×g=W`; ритм `pitch=h+g`; выравнивание `x₁=x₂`; локальная шкала `sᵢ=kᵢ×b+εᵢ`. Последняя формула описывает подгонку, не требование к UI. Коэффициенты и базовый шаг не должны подбираться без ограничений ради красивого ответа.
Каждое отношение хранит ссылки на исходные измерения, область применимости и точные значения. Округление подписи, неопределённость измерения и допуск нормативной проверки — три разных понятия. `≈` сопровождается доступным отклонением; без заданного допуска нельзя превращать близость в pass или точное равенство.
Кандидаты объединяются по явному контейнеру/семейству, типу величины, единицам, bounds kind и совместимому наблюдению. Геометрическая близость не доказывает семантическое родство. CSS px, native points, разные frames, layout и clipped bounds не смешиваются.
Для предполагаемой шкалы показываются поддержка и исключения, а не выдуманный процент уверенности. Повтор одной кнопки 14 раз не равен 14 независимым подтверждениям глобальной шкалы. Подбор мельчайшего общего делителя всегда найдёт «сетку», но почти ничего не объяснит. Автоматический поиск шкал предлагается отложить до отдельной проверки на новых примерах.

## Проверка идеи на реальной форме PlayPhrase.me

Источник: сохранённый DOM reference `dom-layout.json` в `/var/folders/px/srfnff157mg33175_4y8yrnr0000gn/T/uib-mobile-filters-OBW93z`; контекст из `handoff.md`. Viewport 390 × 844 CSS px, DPR 1. Это сохранённый неатомарный browser reference с частичным охватом, не новый live capture и не native iOS. Ниже числа повторно прочитаны из raw bounds; формулы — исследовательские вычисления, не результат новой команды продукта.

| Источник/отношение | Математика | Понятная подпись |
| --- | --- | --- |
| Years: dom-27/28; края 12, 191, 199, 378 | `W=378−12=366; g=199−191=8; w=(366−8)/2=179` | «Два равных поля делят строку после вычета промежутка 8». |
| Viewport и те же крайние границы | `12+366+12=390` | «Группа полей расположена по центру, боковые поля по 12». Это измеренные поля, не доказанный CSS padding. |
| Genres: dom-34…47, две колонки, семь рядов | `w=179; h=40; gₓ=gᵧ=8; pitch=40+8=48` | «14 одинаковых кнопок; шаг рядов 48 состоит из высоты 40 и зазора 8». |
| Отступы Years/Genres и боковые поля | `12=1.5×8`; обе величины кратны 4 | «Боковое поле в полтора раза больше межэлементного зазора». Связь точная; база 4 лишь возможное объяснение. |

Контрпример уже на этой форме: Source dom-20…22 имеет промежутки 2 и ширины 118.6640625; ширина Years 179 также не кратна 4. Это не ошибка дизайна: ширины могут распределять остаток контейнера. Поэтому не объявляем всю страницу сеткой 4/8 и не округляем её геометрию под гипотезу. Cast dom-59 имеет layout-высоту 44, но виден только участок 27; он не становится отдельным размером контрола.
Равенство в одном viewport не доказывает responsive-правило. Для утверждения «при изменении ширины поля всегда делят остаток поровну» нужна декларация layout или отдельные наблюдения; одних совпавших чисел недостаточно.

## Как включить в prompt без нового шума

Предложение: короткий блок «Связи размеров», 2–4 наиболее полезных отношения на лист с существующими якорями. Приоритет — объясняющие структуру связи, затем повторения; не дублировать каждую размерную линию формулой. Это предварительный бюджет представления, не новая нормативная константа.
Пример содержимого для сохранённой mobile-формы: «Years: два поля по 179, между ними 8; вместе 366. Genres: 14 кнопок 179 × 40; шаг рядов 48 = 40 + 8. Боковые поля 12 — в полтора раза больше зазора 8». Словесное объяснение основное, короткая формула рядом при пользе.
ImageGen получает уже вычисленные отношения и подписи. Он не ищет скрытые токены, не рассчитывает размеры и не исправляет оригинальную геометрию под красивую шкалу. Гипотезы не помещаются на лист как доказанные правила; неизвестная причина выбора так и остаётся неизвестной. Голубой/белый outline-only стиль и точные machine facts сохраняются.
Для coding AI тот же набор должен отвечать «какие размеры связаны и чем это подтверждено». Объявленная зависимость позволяет обсуждать последствия изменения; совпадение размеров — только текущую геометрию. Не заявляем исполнение constraints там, где backend показал лишь результат layout.

## Основание в проекте и наблюдаемая реализация

Полная актуальная closure ранее прочитана в этой задаче/сессии; registry проверен повторно, недостающие EXCHANGE/CLI перечитаны. Governance: implementation и product-truth routes; QA для предложенной проверки. Нормативные revisions не меняются.
**Требования контрактов:** единый engine для геометрии; source declarations/expectations отдельно от измерений; явный контекст и bounds kind; точные machine values; rounding только в представлении; неизвестность не скрывается. Эти ограничения уже действуют.
**Наблюдаемый код:** [engine arithmetic](../../../crates/engine/src/arithmetic.rs) реализует Width/Height, Gap, Aligned, EqualSpacing. Ratio сейчас вычисляет width/height одного прямоугольника, а не отношение произвольных измерений. [Валидатор](../../../crates/schema/src/analysis/validation.rs) закрепляет соответствующую арность. [Экспорт](../../../crates/export/src/compile.rs) собирает prompt из Scene/ViewDimensions и [шаблона](../../../crates/export/src/prompt-template.txt). Универсальное объяснение cross-element отношений не следует из наличия Ratio.
**Предложение агента:** модель доказательств, словарь связей, отбор коротких объяснений и этапы ниже. Это не наблюдаемая существующая возможность и не доказанное повышение качества ImageGen.

## Конечный план реализации для согласования

1. Зафиксировать additive contract delta для отношений в analysis/export: явные operands/evidence, точные связи vs гипотезы, применимость к snapshot, запрет придуманного intent. Владельцы: выбранные analysis/drawing leaves и registry; текущие версии/старые входы защищены. Не менять core Snapshot ради текста объяснений. При необходимости нового serialized формата определить versioning до кода.
2. В engine добавить минимальную композицию проверенных измерений для равенства, кратности и распределения доступной ширины; переиспользовать resolution/контекст/арифметику. Владельцы: `crates/engine/src/arithmetic.rs` и применимые analysis owners; schema analysis только при необходимом serialized результате. Не переопределять существующий Ratio и не писать второй калькулятор в exporter; произвольный eval/constraint solver не нужен.
3. В export сформировать детерминированные человеческие объяснения с якорями и передать краткую выборку в actual CLI-generated prompt. Владельцы: `crates/export/src/{types,compile}.rs`, `prompt-template.txt`, при необходимости existing package owner. Явно объявленный шаг можно объяснять; автоматическую догадку о глобальной дизайн-системе в первый этап не включать. Не добавлять отдельный LLM-вызов, команду или настройки без конкретной необходимости.
4. Проверить отношения/отсутствие ложных причин на сохранённых mobile и desktop примерах; focused engine/export tests: равные колонки с зазором, повторение, дробные остатки, одинаковые округлённые подписи при разных raw values, разные spaces/units, clipped bounds, неизвестность/нулевой делитель, значение без token binding. Изменение product contracts потребует актуализировать только затронутые проверки совместимости, без общего повторения P0–P7.
5. Для качества промпта проверить fresh ImageGen результат на тех же реальных формах с literal CLI prompt: корректные связи, читаемость, отсутствие лишних подписей и выдуманных оснований. Показать изображения и ограничения; такую визуальную приёмку не заменять тестами строк. До её запуска сверить применимые drawing acceptance требования; старые 6/6 не принимают новый prompt автоматически. Отдельная короткая пользовательская проверка: по blueprint объяснить ширину поля и восстановить группу; это прямее проверяет понятность, чем количество формул.

Предлагаемый первый результат: измерение → доказанная связь → короткая подпись в автоматически созданном prompt. Вне первого этапа: автоматическое восстановление всей дизайн-системы, массовый импорт DTCG/Figma, изменения сайта, новые collectors, polling, redesign, глобальный solver и причинные объяснения без источника.
Неопределённость перед реализацией: точный additive формат отношения выбирается после проверки затронутых consumers; пороги распознавания приблизительных шкал не установлены, поскольку автоматическое распознавание отложено. На согласование вынесен именно этот первый объём; исследование не даёт разрешения на его реализацию.

## Дополнение: рекомендации по согласованности

Основание 2026-10-11: пользователь предложил получать рекомендации из закономерностей, например при зазорах 4 и 5 px. После предложения различать нарушение известного правила, возможную несогласованность и объяснимое исключение ответил **«Хорошо, согласен.»** Продуктовое направление согласовано. Ниже — уточнение технического плана; существующие Active contracts и код этим документом не меняются.

Пользовательский результат: **где отличается → относительно чего → насколько → что проверить/изменить → какой эффект ожидается**. Сигнал опирается на конкретную группу/правило. Общего довода «мозг любит систему» недостаточно, чтобы объявить размер ошибочным. Исходный blueprint сохраняет фактическую геометрию, рекомендации идут отдельно. Первая очередь объяснений выше сохраняется; рекомендации — следующий потребитель тех же доказательств.

| Случай | Предлагаемое сообщение | Основание |
| --- | --- | --- |
| Известное правило | «Зазор 5 px; правило требует 4 px с допуском 0. Проверьте применение указанного правила». | Действительные Expectation, applies_when, expected_from и engine check. Допуск 0 здесь условный пример, не default. |
| Повторяющийся паттерн | «У семи сопоставимых кнопок зазор 4 px, у одной — 5 px. Проверьте исключение; 4 px согласует его с этой группой». | Установленные семейство, состояние и контекст; точные измерения, участники и исключения. Гипотеза, не fail. |
| Объяснимое исключение | «Отличие предусмотрено для этого варианта компонента». | Подтверждённая декларация/решение. Оптическая поправка, border или масштаб не придумываются как удобная причина. |

Сравниваются исходные величины одного смысла, а не округлённые подписи; учитываются units, bounds kind, состояние, пространство, применимость и доступная неопределённость. Неизвестная сопоставимость не становится уверенной рекомендацией. Разные остатки колонок, обрезка и component variants сами по себе не дефекты. Частичная выборка не представляет всю страницу. Частота значения не является вероятностью правильности или авторским требованием.
Нет автоматического округления к 4/8 px, порога «лишний пиксель — ошибка» или изменения UI. Предложение объясняет локальный ожидаемый эффект; безопасность изменения всего layout подтверждается отдельно. Для inequality-правила сохраняется смысл: «не меньше 4» не превращается в «сделать ровно 4».

### Порядок внедрения

1. **Известное нарушение:** переиспользовать `engine::check` и GeometryCheckCase с настоящим Expectation; imported результат перепроверять `verify_analysis_result`. Показывать actual, comparison/expected/tolerance, правило и применимость. Pass/unknown не превращать в нарушение. До кода закрепить привязку check input к export view: Snapshot сам не содержит нормативного ожидания.
2. **Возможное исключение:** bounded анализ явно выбранного семейства зазоров; сохранять участников, основание группировки, контекст и исключения. Арифметика остаётся в engine. Равная роль или соседство сами по себе не доказывают сопоставимость. Без устойчивого образца показывать факты без предлагаемого «правильного» значения. Автоматическое восстановление глобальной шкалы остаётся вне объёма.
3. **Blueprint/prompt:** короткий отдельный блок с существующими якорями и основаниями; «проверьте» для гипотез. Однотипные сигналы объединять. ImageGen отображает готовые выводы, не вычисляет и не исправляет исходник. Новые machine fields, если понадобятся, получают явную совместимость до реализации; core0.1/analysis0.2 и смысл Ratio защищены.
4. **Проверка:** независимые случаи правило 4/факт 5, отличие внутри допуска, минимум 4/факт 5, unknown; группа 4/4/4/5, отсутствие доминирующего значения, разные состояния/spaces, одинаковые округлённые подписи при разных raw values. Затем сохранённая реальная форма: подтверждённые основания либо честное отсутствие рекомендации. Визуальную проверку нового блока выполнить после реализации; прежняя приёмка изображений не переносится автоматически.

Наблюдаемые владельцы: `crates/engine/src/lib.rs` (`check`, `measure_query`), `crates/engine/src/analysis.rs` (привязка/пересчёт), `crates/export/src/{types,compile,observed}.rs`, `prompt-template.txt`. Перед реализацией уточняется минимальный формат передачи правил/семейств и соответствующий analysis/drawing/CLI-export contract delta. Новые collectors, сайт, дополнительные чаты и автоматические исправления не требуются. Работа остаётся single-agent; согласование подхода не запускает новую persistent goal.
